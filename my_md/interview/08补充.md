# 关键词检索、向量检索的实现方式？

## 关键词检索：

   一、整体召回链路
  用户问题进来后，不是所有路径都会先做 query_rewrite。当前默认更准确的说法是：

  > 原始 query 进入召回；部分路径会额外生成 aux_queries 或轻量假设 query，用来增强向量召回。关键词检索只吃原始 query，向量检索吃 原始 query + aux_queries，最后做 RRF 融合。

  也就是：

  用户问题
    -> 原始 query
    -> 可选生成 aux_queries / 假设 query
    -> 关键词 lane：只用原始 query
    -> 向量 lane：用原始 query + aux_queries
    -> RRF 融合排序
    -> 返回候选记忆

  二、关键词检索怎么做
  关键词检索很朴素，核心是：

  切词 -> SQLite LIKE 匹配 -> 命中数打分 -> 排序截断 -> 和向量结果融合

  它不是 BM25，也不是语义检索。

  三、切词逻辑
  _extract_terms() 会从用户 query 里抽关键词：

  英文、数字、技术词：
  用正则抓连续 token，比如：

  memory2
  yt-dlp
  v1.2.3
  agent_runtime

  中文/日文：
  先抓连续中文块。

  - 如果长度 <= 4，整块保留
  - 如果长度 > 4，拆成重叠的 2 字 bigram

  比如：

  中文检索流程优化

  会拆成：

  中文
  文检
  检索
  索流
  流程
  程优
  优化

  然后过滤停用词，比如“用户、这个、什么、最近、之前”等低信息量词，最后去重，只保留前 20 个词元。

  所以要记住：

  > 不是最多 20 个汉字，而是最多 20 个有效词元。中文长句会被拆成多个 2 字片段，后面的词元超过 20 个后不参与关键词检索。

  四、SQL 检索逻辑
  切出来的每个 term 会变成：

  %term%

  然后拼成：

  summary LIKE ? OR summary LIKE ? OR ...

  也就是说，它是在 memory_items.summary 上做子串包含匹配。

  同时还会加过滤条件：

  status = active
  memory_type 可选过滤
  scope_channel / scope_chat_id 可选过滤
  time_start / time_end 可选过滤

  五、排序逻辑
  每条记忆会算一个 kw_score：

  kw_score = 命中的 term 数量
  keyword_score = kw_score / terms 总数

  排序规则是：

  kw_score DESC
  reinforcement DESC
  id ASC

  意思是：

  1. 命中关键词越多越靠前
  2. 命中数一样时，被强化次数更多的靠前
  3. 再一样时按 id 保持稳定顺序

  六、一句话背诵版
  可以这么说：

  > 这个项目的关键词检索不是 BM25，而是轻量的 SQLite LIKE 检索。它先把用户 query 切成最多 20 个词元，英文数字用正则抽 token，中文长句拆成 bigram，并过滤停用词。然后在
  > memory_items.summary 上做 LIKE 子串匹配，按命中词数、reinforcement 和 id 排序，得到关键词候选。关键词 lane 只使用原始 query，不使用 aux_queries，最后再和向量 lane 做 RRF
  > 融合。

## 向量检索：

量检索的逻辑可以概括成：

  > 用户 query -> 生成 query embedding -> 到 memory item 的 embedding 里做相似度检索 -> 返回 top-k 记忆候选。

  具体流程是：

  1. 准备 query 列表
     Retriever 会把原始 query 和 aux_queries 合在一起去重。
     也就是说，向量 lane 会吃：raw query + aux_queries。
     关键词 lane 不吃 aux，只吃 raw query。见 memory2/retriever.py:214

  2. 生成 query embedding
     _embed_lanes() 会并发调用 Embedder.embed()，每条 query 最多等 8 秒。失败的 query 会跳过，不会让整个检索失败。见 memory2/retriever.py:390

  3. 走 SQLite 向量索引
     MemoryStore2 启动时如果检测到 sqlite_vec，会创建 vec_items 虚表，把已有 memory_items.embedding 迁移进去。见 memory2/store.py:292

  4. KNN 检索
     查询时用 embedding MATCH ? 在 vec_items 里做最近邻检索，再 join 回 memory_items 拿 summary、type、source_ref 等字段。见 memory2/store.py:1207

  5. 相似度计算
     存进去的 embedding 会做 L2 归一化，所以 sqlite-vec 返回的 L2 distance 可以换算成 cosine similarity。
     然后先过 score_threshold，默认 retriever 阈值大概是 0.45。见 memory2/store.py:1089

  6. 热度融合
     最终分数不是纯语义分。它会把 semantic similarity 和 hotness 混合：
     final = (1 - alpha) * semantic + alpha * hotness
     hotness 受 reinforcement、更新时间、emotional_weight 影响。默认 hotness_alpha 在 Retriever 里是 0.20。

  7. fallback
     如果 sqlite-vec 不可用、维度不匹配，或者带了时间过滤，就回退到 Python 全表扫描，用 numpy 计算 cosine similarity。见 memory2/store.py:1345

  8. 多 query 去重
     如果 raw query 和 aux query 都命中了同一个 memory item，会按 id 去重，保留分数更高的那条。

  一句话总结：

  > 向量检索是用 embedding 做语义相似度召回，优先走 sqlite-vec KNN，失败时退回全表 cosine；raw query 和 aux_queries 都参与向量检索，最后结果再和关键词 lane 做 RRF 融合。

• 这几个是 Embedder 调 embedding API 时的工程细节。

  - 单条文本会调用 embed_batch([text])
    代码只维护一个批量接口。即使你只查一句话，也会包装成数组：

  ["我之前喜欢用什么语言？"]

  然后复用批量逻辑。

  - 每批最多 10 条
    如果一次要 embed 25 条 query，会拆成：

  第 1 批：10 条
  第 2 批：10 条
  第 3 批：5 条

  这是为了适配 DashScope embedding 接口的批量上限。

  - 每条文本最多截断到 2000 字符
    太长的 query 不会完整送去 embedding，只取前 2000 字符，避免请求过大、成本过高或接口报错。

  - 请求超时 30s，总 budget 40s
    单次 HTTP 请求最多等 30 秒；整体预算最多 40 秒。超过就失败，不会无限卡住 agent。

  - 返回后按 index 排序，取 embedding
    批量请求时，API 返回的数据里每条 embedding 会带一个 index，表示它对应输入数组里的第几个文本。
    代码会先按 index 排序，保证返回顺序和输入顺序一致。

  比如输入是：

  ["query A", "query B", "query C"]

  即使 API 返回顺序乱了，也会重新排成：

  [
    embedding_of_query_A,
    embedding_of_query_B,
    embedding_of_query_C
  ]

  这样后面才能知道哪个向量对应哪个 query。

› 1. 把距离转换成 cosine similarity
    2. 过滤低于阈值的结果
    3. 加一点 hotness 分数
    4. 多个 query 命中的结果按 memory id 去重，保留分数更高的那条
  这是什么意思？


• 这 4 步是在把“向量库返回的原始候选”变成“可排序、可用的记忆候选”。

  1. 把距离转换成 cosine similarity

  sqlite-vec 返回的是距离，距离越小越相似。
  但后面系统更习惯用 similarity，分数越大越相似。

  因为存进去的向量做过归一化，所以可以把 L2 distance 转成 cosine：

  cosine_similarity = 1 - distance² / 2

  直觉上：

  distance 小  -> similarity 高
  distance 大  -> similarity 低

  2. 过滤低于阈值的结果

  不是搜到什么都要。
  如果 similarity 太低，说明这条记忆和问题关系弱，就丢掉。

  例如阈值是 0.45：

  score = 0.72  保留
  score = 0.51  保留
  score = 0.31  丢弃

  3. 加一点 hotness 分数

  项目不是只看语义相似度，还会考虑这条记忆是不是“更常用、更近期、更重要”。

  hotness 大概受这些因素影响：

  reinforcement      被反复强化过
  updated_at         最近更新过
  emotional_weight   情绪/重要性权重更高

  最终分数类似：

  final = 0.8 * semantic_score + 0.2 * hotness_score

  所以一条稍微没那么语义相似、但最近经常被用到的记忆，也可能排名靠前一点。

  4. 多个 query 命中同一条记忆时去重

  因为向量检索会同时用：

  原始问题
  aux query 1
  aux query 2

  它们可能都搜到同一个 memory item。

  比如：

  原始问题 -> 命中 memory_123，score 0.68
  aux query -> 命中 memory_123，score 0.75

  系统不会保留两条重复结果，而是：

  memory_123 只保留一次，取更高分 0.75

  这样避免同一条记忆重复进入后续融合和 prompt。





## 证据链路：

• 以 provenance lane 为主，一步一步是这样：

    1. 用户问题进来
     比如：我之前说过默认用什么语言？
    2. 先拿到当前 active memory
     系统会从 memory store 里取一批 status = active 的记忆，不是直接查向量库。
    3. 做基础过滤
     只看符合当前 memory_type、时间范围、scope 要求的记忆。如果当前场景要求同 scope，就只保留同 scope_channel / scope_chat_id 的记忆。
    4. 进入 provenance lane
     调 build_provenance_lane(query, active_items, scope_channel, scope_chat_id)。
    5. 丢掉没有来源的记忆
    6. 对 query 和 summary 做轻量切词
     英文数字用正则取词；中文按 2 字片段做 overlap。比如“默认语言”会产生类似“默认”“认语”“语言”这样的二字片段。
    7. 算 provenance_score
      - query 有“之前/上次/那个/刚才”这种模糊指代：加 0.35
      - memory 和当前会话 scope 匹配：加 0.25
    8. 排序返回 provenance_items
     按 provenance_score 从高到低排序，最多返回 limit 条。
    9. 再参与三路融合
    
     最后 provenance lane 会和 vector lane、keyword lane 一起进入 RRF 融合排序。

  一句话：provenance lane 是先从 active memory 里找有 source_ref 的记忆，再按“词重叠 + 模糊指代 + 同 scope”打分，把可追溯证据作为第三路召回结果送进融合。



2. 代码里不是全量扫 active memory，而是先取一个窗口：page_size=max(200, top_k*20)。默认 top_k 是 8，所以默认会取 200 条 active memory，再从里面筛。

• 默认是 最多取 200 条 active memory。

  具体代码是：

  active_items, _total = self._store.list_items_for_dashboard(
      status="active",
      page_size=max(200, top_k * 20),
  )

  默认 top_k = 8，所以：

  max(200, 8 * 20) = 200

  也就是说，provenance lane 不是扫全库，而是先从 memory store 里取最近/排序靠前的一批 active 记忆，默认 200 条。然后再过滤 memory_type、scope、source_ref，最后 provenance
  lane 自己最多返回：

  max(20, top_k * 2)

  默认就是 20 条 provenance candidates，再参与三路融合。

3.• 拿到这 200 条 active memory 后，下一步是 先做基础过滤。

  主要过滤两类：

  1. memory_type 过滤
     如果当前请求指定了 memory_types，就只保留这些类型。
     比如只查 preference/profile/event 里的某几类。

  2. scope 过滤
     如果当前 route 要求 require_scope_match=True，就只保留当前会话同 scope 的记忆：
      - scope_channel 一致
      - scope_chat_id 一致

  过滤完得到 filtered_items。

  然后才进入：

  build_provenance_lane(query, filtered_items, scope_channel, scope_chat_id)

  也就是说流程是：

  取 200 条 active memory
  -> 按 memory_type 过滤
  -> 按 scope 过滤
  -> 得到 filtered_items
  -> 交给 provenance lane 打分

  这一步还没有开始算 provenance_score，只是在缩小候选范围。

• **memory_type 是记忆类型，当前项目里主要用这几类：**

  - **event**：事件/历史片段，比如“某次对话里发生过什么”
  - profile：用户画像/长期事实，比如状态、身份、购买、长期信息
  - **preference**：偏好，比如“用户喜欢中文回答 / 偏好某种语言”
  - **procedure**：流程/工具使用规则，比如“遇到某类任务优先用某个工具或步骤”

  scope 是这条记忆所属的上下文范围，用来防止不同入口、不同会话之间串记忆。

  代码里 scope 拆成两个字段，放在 extra_json 里：

  - scope_channel：来源渠道，比如 cli、telegram
  - scope_chat_id：具体会话 ID，比如 local、某个群/私聊 id

  所以：

  scope_channel 一致
  scope_chat_id 一致

  意思是：这条记忆必须来自当**前同一个渠道、同一个会话。**

  举例：

  当前用户是在：

  scope_channel = telegram
  scope_chat_id = 100

  那么一条记忆如果是：

  scope_channel = telegram
  scope_chat_id = 100

  就算同 scope，可以进入候选。

  如果是：

  scope_channel = cli
  scope_chat_id = local

  或者：

  scope_channel = telegram
  scope_chat_id = 200

  就不是同 scope，在要求 require_scope_match=True 的场景会被过滤掉。

  面试里可以说：**memory_type 是内容类别过滤，scope 是会话边界过滤；前者决定查哪类记忆，后者防止跨聊天、跨平台误召回。**

4.• 前面过滤只是把候选缩小到“类型对、scope 对”的 active memory。

  进入 build_provenance_lane(...) 后，才真正开始做 provenance 这一路自己的召回打分。

     英文/数字用正则取词，中文按连续 2 字片段切。

把每条 memory 的 summary 也切成 terms
然后计算 query terms 和 summary terms 的重叠数量。
分数来自几部分：

 - query-summary 有词重叠，加分
 - query 里有“之前/上次/那个/刚才”等模糊指代，加 0.35
 - memory 和当前 scope 完全一致，加 0.25
 - 记忆在 active 列表里越靠前，加一点很小的顺序分

排序返回
没有任何信号的候选丢掉，有分数的按 provenance_score 降序，最多返回默认 20 条。

  一句话：前面过滤是“能不能进 provenance lane”，build_provenance_lane 是“进来以后谁更像可追溯证据”。


​    这里memory经过过滤，不是一定和scope一致吗？


• 不一定。

  前面的 scope 过滤只有在 require_scope_match=True 时才会强制执行：

  如果 require_scope_match=True：
      只保留同 scope 的 memory
  如果 require_scope_match=False：
      不按 scope 过滤，其他 scope 的 memory 也可能留下

  而很多普通召回场景里，require_scope_match 默认是 False。比如未知场景、模糊指代、工具偏好，通常不会一开始强制只查同 scope。

  所以进入 build_provenance_lane 后，还要再判断一次：

  scope_match = item.scope_channel == current_scope_channel
            and item.scope_chat_id == current_scope_chat_id

  如果一致，就给 provenance_score 加 0.25。

  也就是说：

  - 强 scope 场景：前面已经过滤过，进入 provenance lane 的基本都同 scope，这个 +0.25 相当于强化排序。
  - 非强 scope 场景：前面没有过滤，provenance lane 里可能有跨 scope 候选，同 scope 的会被加分排前面。

  面试里可以说：scope 既可以作为硬过滤，也可以作为软排序信号；是否硬过滤取决于 retrieval route。

 这个是否类似关键词检索？


• 有点像，但目的不一样。

  相同点：

  - 都会对 query 和 summary 做轻量词元匹配。
  - 都会看字面 overlap。
  - 都不依赖 embedding。

  不同点：

  keyword lane 是真正的关键词检索：

  query 切词
  -> SQLite summary LIKE
  -> 按命中词数 / 总词数算 keyword_score

  它关注的是：summary 里有没有字面命中用户问题里的词。

  provenance lane 是来源证据召回：

  先拿 active memory
  -> 只保留有 source_ref 的记忆
  -> query-summary overlap
  -> 模糊指代加分
  -> 同 scope 加分
  -> 返回可追溯候选

  它关注的是：这条记忆是不是有来源、是不是同上下文、能不能作为可追溯证据。

  所以可以这样说：

  provenance lane 借用了类似关键词 overlap 的轻量匹配，但它不是关键词检索；它多了 source_ref、scope、模糊指代这些证据治理信号，目标是补充“可追溯的上下文证据”。



# sqlite-vec与全表扫描

 你把现在吧我问的有关sqlite-vec和退化的全标扫描内容总结一下


• 可以，简要总结如下：

  1. sqlite-vec 是什么

  - 专门做向量最近邻检索的 SQLite 扩展。
  - 项目里会建一个 vec_items 虚表，把 memory_items.embedding 同步进去。
  - 查询时用 embedding MATCH ? 做 KNN，直接找最近的 top-k 记忆。

  2. sqlite-vec 可用时怎么走

  - query 先做 embedding。
  - 每个 query vector 单独发起一次 KNN。
  - sqlite-vec 在扩展层里找最近邻，返回 rowid 和 distance。
  - 再 join 回 memory_items，算最终 score、hotness、去重。

  3. sqlite-vec 不可用时怎么走

  - 仍然保留 memory_items.embedding。
  - 先把所有有 embedding 的 memory item 取出来。
  - Python / numpy 逐条算 cosine similarity。
  - 排序取 top-k。

  4. 为什么会慢

  - 因为没有向量索引，只能逐条比较。
  - 不是主键问题，普通主键/B-tree 也解决不了“找最近向量”这种问题。
  - 数据量一大，Python 层全扫会很重。

  5. 时间范围过滤时为什么也退化

  - 为了保证只在指定时间范围内找候选，当前实现会先按时间筛出 memory item。
  - 然后在这个候选集里做向量相似度计算。
  - 这时不会直接走 sqlite-vec 的 KNN 路径。

  6. KNN 和全表扫描的区别

  - 语义上都在找最近邻。
  - 实现上不同：
      - KNN：交给 sqlite-vec 扩展层处理
      - 全表扫描：Python 逐条算距离

  - 所以 KNN 更适合大规模数据，全表扫描是退化兜底。

  7. 当前项目里的实际结论

  - sqlite-vec 可用时：优先走向量索引检索。
  - 不可用或受时间过滤限制时：退化为全表/候选扫描。
  - 功能还能跑，但速度会明显差。

# 召回处理全流程

• 不是简单“各路排序后直接 RRF”。当前主流程更准确是：

  1. 各 lane 先召回
      - semantic/vector
      - keyword
      - provenance
      - 有些场景还会有 graph，但 graph 不是三路基础项

  2. 先做 retrieval route / 候选准入
     系统根据 query 判断场景，例如：
     
      - 模糊指代
      - 精确召回
      - 来源查询
      - 冲突问题
      - 工具偏好
     
     然后决定哪些 lane 能进、每个 lane 最多保留几条、是否要求 source、是否要求同 scope、是否丢低置信。
     
  3. 候选治理在 RRF 前做一轮
     apply_retrieval_route(...) 会对每个 lane 的候选做：
      - lane 是否允许
      - lane cap 截断
      - missing_source_ref
      - scope_mismatch
      - low_confidence
      - duplicate 去重
      - 如果启用 candidate governance，还会标 delete / requires_review / downgrade / allow

  4. 然后才做 RRF 融合
     对治理后留下的 accepted_by_lane 做 RRF：
     
      - semantic 权重 1.0
      - provenance 权重 1.0
      - keyword 权重 0.5
      - 多 lane 命中的候选会被抬高
      - 最后截断到 top_k
     
  5. 融合结果先生成普通 memory injection block
     也就是把最终 items 渲染成要注入给模型的记忆文本。

  6. 结构化证据 contract 在 RRF 之后做
     如果开启 safe_version_governed_mode=shadow/replace，会调用：

     build_system_path_safe_version_contract(...)

     它会基于 RRF 后的结果和 route trace，再做一层结构化证据整理：
      - allowed_evidence
      - likely_relevant_evidence
      - active_version
      - stale_warning
      - conflict_warning
      - forbidden_boundary
      - deleted_evidence
      - insufficient_evidence_fallback

  7. 回答引导 answer guidance 最后渲染进注入块
     如果 replace 且开启 guidance，就用 evidence contract 替换普通 memory block，并加入指令：
      - 只根据 allowed_evidence 回答
      - 优先 active/current truth
      - 不使用 deleted/superseded/forbidden/cross-scope 证据
      - 证据不足就说记忆不足

  所以一句话：

  三路召回后不是直接给模型，而是先做 route/candidate governance，再 RRF 融合；RRF 之后生成结构化 evidence contract，最后通过 answer guidance 约束模型如何使用这些记忆回答。

```
  accepted provenance candidates

  就是每一路最终允许进入 RRF 的候选列表。

  所以面试里可以说：

  accepted_by_lane 是 route + candidate governance 之后的分 lane 候选池。它保留了每一路最终通过准入的候选，RRF 只对这些 accepted candidates 做融合排序。
```

  一句话：最佳方案在 RRF 前不是直接融合三路结果，而是先按 query 场景做 route，再做 source/scope/低置信/风险分层治理，删除危险候选、标记弱证据、去重并限流，最后才把治理后的候  选交给 RRF。

**这种重合的场景该怎么回答？**

  这里确实有重合，但不是重复设计，而是两层防线。

  第一层是 route governance，它按“问题场景”做准入。比如用户问来源或冲突，这类问题天然要求证据可追溯、同 scope，所以 source_ref 和 scope 会变成硬条件，不满足就直接不进 RRF。

  第二层是 candidate governance，它按“候选本身风险”做分层。即使当前场景没有强制要求 source 或 scope，它也会识别候选是否缺来源、弱来源、低置信、冲突、旧版本，然后标成  delete / requires_review / downgrade / allow。

  如果面试官追问“那不是重复了吗”，可以回答：

  有交叉，但职责不同。route 是 query-level 的策略，解决“这个问题应该开放哪些召回通道、需要什么证据门槛”；candidate governance 是 item-level 的治理，解决“这条候选本身能不能作  为证据”。同一个信号，比如 source_ref，在来源查询里是硬门槛；在普通问题里可能只是候选风险，进入 review 或 downgrade。

  可以举例：

  问题：这条记忆的来源是什么？
  route 层：必须有 source_ref，没有就直接丢。

  问题：我之前喜欢什么语言？
  route 层：不一定强制 source_ref。
  candidate governance 层：如果某条候选没有 source_ref，会标 missing_source_ref，进入 requires_review，不作为最强证据。

  最后收一句：

  所以重合是有意的：route 先按场景收窄候选边界，candidate governance 再按证据质量做风险分层，避免三路召回把噪声、旧版本和跨 scope 记忆直接送进 RRF 和回答上下文。

从这些流程总结一下，适合在**面试上说的，从三路召回后到进入RRF之前**


 面试里可以这样说：

  三路召回之后，我们不是直接把 semantic、keyword、provenance 的结果送进 RRF，而是先做一层 route governance + candidate governance。

  第一步是根据 query 做场景路由。系统用轻量规则判断问题属于普通召回、精确查询、来源查询、冲突问题、工具偏好或模糊指代。不同场景会生成不同的 route policy，比如允许哪些 lane  进入、每个 lane 最多保留多少条、是否要求 source_ref、是否要求同 scope、是否丢弃低置信候选。

  第二步是执行这个 policy。比如当前问题是来源查询，就会优先 provenance，并要求候选必须有 source_ref、必须同 scope；如果是精确查询，就优先 keyword，再补 semantic；如果是普通  问题，就只开放 semantic 和 keyword，避免 provenance 噪声进入。

  第三步是做候选风险治理。系统会对每条候选现场识别风险，不是依赖一个预先写好的 risk 字段。它会看候选的 status、source_ref、scope_match、confidence、summary、tags、extra_json  等字段，判断是否存在 forbidden、旧版本、跨 scope、冲突、缺来源、弱来源、低置信、证据不足等问题。

  第四步是把风险映射成治理动作。最佳方案里用 tiered governance：forbidden / superseded / scope_mismatch 直接 delete；conflict / missing_source_ref / insufficient_evidence 进  入 requires_review；weak_source_ref / low_confidence 进入 downgrade；没有风险的就是 allow。

  第五步是按 lane cap 和去重生成 accepted_by_lane。也就是每一路最终允许进入排序的候选池，比如 accepted semantic、accepted keyword、accepted provenance。只有这些治理后的候选  才会进入 RRF。

  如果面试官问为什么 route 和 candidate governance 有重合，可以说：route 是 query-level，解决“这个问题应该开放哪些通道、证据门槛多高”；candidate governance 是 item-level，解  决“这条候选本身能不能作为可信证据”。两者在 source、scope、low confidence 上有交叉，但一个是场景硬准入，一个是候选质量分层。

# RRF融合排序

› 融合排序是怎么做的？• 融合排序用的是 RRF：Reciprocal Rank Fusion。

  它的核心思想是：

  > 不直接相信某一个 lane 的分数，而是看一条记忆在各个 lane 里的排名。如果同一条记忆在多个 lane 都靠前，它就应该排得更靠前。

  公式大概是：

  rrf_score += lane_weight / (k + rank)

  项目里：

  k = 60
  keyword lane weight = 0.5
  其他 lane weight = 1.0

  举个例子。

  向量检索结果：

  semantic lane:
  1. A
  2. B

  关键词检索结果：

  keyword lane:
  1. B
  2. C

  那么 RRF 会算：

  A = 1.0 / (60 + 1)

  B = 1.0 / (60 + 2)
    + 0.5 / (60 + 1)

  C = 0.5 / (60 + 2)

  结果是：
  B 可能排第一，因为它虽然在向量里是第 2，但它同时被关键词 lane 命中了。

  这就是 RRF 的价值：

  单路靠前        有加分
  多路都命中      加更多分
  关键词命中      有加分，但权重较低

  最后排序时主要看：

  rrf_score
  lane_hits 数量
  原始 best_score
  item_id

  所以融合排序不是简单“向量分数高就第一”，而是：多路召回共同认可的记忆优先。

  默认情况下，RRF 后的 items 会先被渲染成普通 memory block，比如：

  相关记忆：
  - [mem1] 用户喜欢 Python
  - [mem2] 用户之前说过默认用中文

  所以普通 memory block 会被替换掉，模型最终收到的是治理后的结构化证据和回答约束。

  replace 的作用是让治理结果真正生效。shadow 只记录治理结果不影响回答；replace 会把普通 RRF 记忆块替换成 evidence contract block，确保模型只能看到 allowed evidence 和 answer

# 回答引导

›answer guidance 的具体工作步骤是：

## 拿到 evidence contract  前一步已经生成了结构化字段：

  allowed_evidence
  likely_relevant_evidence
  active_version
  stale_warning
  conflict_warning
  forbidden_boundary
  deleted_evidence
  insufficient_evidence_fallback



 这些是 evidence contract 里的结构化证据字段，用来告诉模型“哪些记忆能用、哪些不能用、哪些要谨慎”。

  逐个解释：

  - allowed_evidence
    允许模型使用的证据文本。回答只能基于这里。

  - likely_relevant_evidence
    在 allowed_evidence 里进一步筛出的更可能相关的证据。回答时优先看这里。

  - active_version
    当前有效版本的证据 ID。比如用户后来更新了偏好，就优先使用最新偏好。

  - stale_warning
    旧版本/过期证据 ID。提示模型这些记忆已经不应作为最终答案依据。

  - conflict_warning
    有冲突风险的证据 ID。说明这些证据之间可能矛盾，回答要谨慎。

  - forbidden_boundary
    明确禁止使用的证据 ID。比如 forbidden、should_not_recall、跨边界污染等。

  - deleted_evidence
    被治理删除的证据 ID。通常是 forbidden、superseded、scope_mismatch 这类不能进入回答的候选。

  - insufficient_evidence_fallback
    布尔值。表示当前证据是否不足。如果是 true，模型应该说“可用记忆不足”，而不是猜。

  一句话：

  这些字段就是 evidence contract 的证据边界：allowed 告诉模型能用什么，active 告诉模型优先用什么，stale/conflict/forbidden/deleted 告诉模型不能或谨慎使用什么，insufficient  fallback 告诉模型证据不够时不要编。

## 选择 guidance variant 根据配置决定使用哪种回答引导，比如：

  standard
  guided
  structured_guided
  near_query_block
  guided_retry_shadow
  schema_first_shadow

  最佳方案里通常是带 guidance 的 variant，而不是纯 standard。



• guided_retry_shadow 是 answer guidance 的一个模板变体，位置在 RRF 后、LLM 前。它的功能是：让模型基于当前可信证据直接回答，不要用旧版本、冲突证据，也不要在证据已足够时继续说“我先查一下”。

  实现分两部分：

    1. 先构建 Answer Candidate Contract

  在 evidence contract 阶段，会根据 allowed evidence / active version / stale evidence 生成一个答案候选契约，里面有：

  current_truth
  stale_truth
  answerable
  must_include_term_count
  forbidden_old_value_ids
  language_requirement

  核心含义：

  - current_truth：当前有效事实，模型应该优先使用
  - stale_truth：旧事实/失效事实，模型不能拿来当答案
  - answerable：当前证据是否足够回答
  - must_include_term_count：答案应覆盖的关键事实数量
  - forbidden_old_value_ids：禁止复述的旧值
  - language_requirement：要求用用户语言回答

    2. 渲染 guided_retry_shadow 模板

  在 render_system_path_evidence_contract_block() 里，如果 variant 是：

  guided_retry_shadow

  会追加类似这些规则：

  Use allowed_evidence as the only source for the answer.
  Use the Answer Candidate Contract to select the final answer.
  Directly answer the user's question first.
  Restate at least one concrete current_truth fact in the answer.
  Only state the current truth from current_truth and allowed_evidence.
  Do not repeat old, stale, or superseded values.
  Normally do not mention replacement history.
  Answer in the user's language.

  如果证据已经足够，还会补一句：

  Do not restart recall, search, fetch, or read memory files...

  也就是提醒模型：现在证据已经给你了，别再假装要查。

  功能上它解决三个问题：

    1. 召回到了但模型没用对
       强制从 allowed_evidence/current_truth 选答案。
    
    2. 旧版本污染
       明确禁止复述 stale/superseded old value。
    
    3. 回答不直接
       要求直接回答用户问题，不输出确认、计划、伪工具调用。

  一句话：

  guided_retry_shadow 是当前最佳 answer guidance 模板，它在 evidence contract 上增加 Answer Candidate Contract，把“可用证据”进一步整理成 current truth 和 forbidden old  value，并用强提示约束模型直接基于当前事实回答。





## 渲染证据边界 先把 contract 里的证据和统计信息渲染成文本：

  Evidence Contract
  allowed_evidence:
  - [id1] ...
  - [id2] ...

  likely_relevant_evidence_count: ...
  active_version_count: ...
  stale_warning_count: ...
  conflict_warning_count: ...
  forbidden_boundary_count: ...
  deleted_evidence_count: ...
  insufficient_evidence_fallback: true/false



• 这是 Evidence Contract 的文本化结果，也就是把内部结构化字段转成模型能读懂的一段 prompt。

  它不是给用户看的，是注入给 LLM 的记忆证据边界。

  里面每一项的作用是：

  Evidence Contract

  告诉模型：下面不是普通聊天内容，而是一份证据契约。

  allowed_evidence

  列出模型可以使用的记忆证据。回答只能基于这里。

  likely_relevant_evidence_count

  告诉模型高相关证据有多少条。用于提醒模型当前是否有直接相关证据。

  active_version_count

  告诉模型当前有效版本有多少条。大于 0 时，回答要优先 active/current version。

  stale_warning_count

  告诉模型存在多少旧版本/过期证据。不要拿旧版本当最终答案。

  conflict_warning_count

  告诉模型有多少冲突风险证据。如果有冲突，回答要谨慎，不能混用矛盾事实。

  forbidden_boundary_count

  告诉模型有多少禁止使用的证据边界。模型不能用这些内容回答。

  deleted_evidence_count

  告诉模型有多少证据已被治理删除。删除的证据不能用于回答。

  insufficient_evidence_fallback

  告诉模型证据是否不足。

  - false：证据足够，直接基于 allowed evidence 回答。
  - true：证据不足，不要猜，要说明可用记忆不足。

  所以这一段的意义是：  把治理后的记忆从“普通候选列表”变成“证据合同”：明确哪些能用、当前版本是否存在、有没有旧证据/冲突/禁用边界，以及证据不足时该怎么处理。

## 加入基础 Instruction 无论哪种 variant，都会有核心约束：

  answer only from allowed_evidence
  如果证据不足，就说可用记忆不足
  不要使用 deleted / superseded / cross-scope / forbidden evidence



这是 Evidence Contract 的基础使用规则。

  前面的 allowed_evidence / active_version_count / stale_warning_count 是告诉模型“证据是什么、状态是什么”。

  这一段 Instruction 是直接告诉模型“你应该怎么用这些证据”。

  核心有三条：

    1. 只基于 allowed_evidence 回答

  answer only from allowed_evidence

  意思是：模型不能把被删除、过期、跨 scope、禁止的记忆拿来回答，也不能自己脑补。

    2. 证据不足时说不足

  If evidence is insufficient, say that the available memory is insufficient.

  意思是：如果 insufficient_evidence_fallback=true，或者 allowed evidence 里没有足够信息，模型应该明确说“当前可用记忆不足”，而不是猜。

    3. 不要使用危险证据

  Do not use deleted, superseded, cross-scope, or forbidden boundary evidence.

  意思是：这些候选即使曾经被召回过，也不能作为答案依据。

  所以这一步的作用是：

  把 evidence contract 从“证据状态说明”变成“模型行为约束”。

  面试里可以说：

  基础 Instruction 是所有 guidance variant 都会带的硬规则，它约束模型只能使用 allowed_evidence，在证据不足时不要编造，并明确禁止使用 deleted、superseded、cross-scope、  forbidden 证据。



## 加入 Answer Guidance 如果开启 guidance，会追加更具体的规则：

  优先使用 allowed_evidence
  优先使用 active version/current truth
  直接回答用户问题
  不要提及 deleted/superseded/forbidden evidence
  使用用户语言



• 这是在基础 Instruction 之上的 更细回答策略。

  基础 Instruction 只说“能不能用什么证据”；Answer Guidance 进一步告诉模型“应该怎么组织答案”。

  具体含义：

  - 优先使用 allowed_evidence
    回答只能围绕允许证据，不从旧记忆或模型常识里补。

  - 优先使用 active version / current_truth
    如果同一偏好有新旧版本，回答当前有效版本，不复述旧版本。
    比如旧记忆是 JavaScript，新记忆是 Python，就直接答 Python。

  - 直接回答用户问题
    不要输出“我帮你查一下”“根据记忆我来分析”等绕弯内容。

  - 不要提及 deleted / superseded / forbidden evidence
    即使系统内部知道旧版本，也不要把旧值说出来污染答案。
    比如不要说“你以前喜欢 JavaScript，但后来改成 Python”，除非用户明确问历史变化。

  - 使用用户语言
    用户中文问，就中文答；英文问，就英文答。

  所以这一步的作用是：

  减少模型“证据用错、旧版本复述、不直接回答、语言不一致”的问题。

  面试里可以说：

  Answer Guidance 是回答层约束，它不改变召回结果，而是指导模型如何使用证据：只用 allowed evidence，优先 current truth，直接回答，避免暴露或复述被删除/过期/禁用证据，并保持用  户语言。

## 如果有 Answer Candidate Contract，加入候选答案约束 在更强的 guided_retry_shadow/schema_first_shadow 里，会加入：

  current_truth
  stale_truth
  answerable
  required_current_facts

  目的是让模型优先选择当前事实，而不是旧事实或冲突事实。



这是 guided_retry_shadow 里更强的一层：Answer Candidate Contract = 候选答案契约。

  前面的 Evidence Contract 解决的是：

  哪些证据能用？
  哪些证据不能用？

  Answer Candidate Contract 进一步解决：

  基于这些证据，最终应该选哪个事实来回答？

  它会把证据整理成更接近“答案选择”的结构。

  核心字段可以这样理解：

  - current_truth
    当前有效事实。模型应该优先用这里回答。

    例子：

    current_truth:
      用户后来明确改为喜欢 Python。

  - stale_truth
    旧事实/失效事实。模型不能拿它当当前答案。

    例子：

    stale_truth:
      用户之前喜欢 JavaScript。

  - answerable
    当前证据是否足够回答用户问题。

    如果证据足够，就直接回答；如果不足，就不要猜。

  - required_current_facts
    回答里必须覆盖的当前事实。

    比如用户问“我喜欢什么语言”，当前事实是 Python，那回答里必须包含 Python。

  当前代码渲染里最明显的字段是：

  Answer Candidate Contract:
  current_truth:
  must_include_term_count:
  forbidden_old_value_count:
  language_requirement:

  含义是：

  - current_truth：当前答案事实
  - must_include_term_count：答案要覆盖多少关键事实
  - forbidden_old_value_count：有多少旧值禁止复述
  - language_requirement：用什么语言回答

  所以这层的作用是：  不是只告诉模型“这些证据能用”，而是进一步告诉模型“应该选择当前事实回答，旧事实不要复述，关键事实必须说到，语言要匹配用户”。

# 底层存储的结构

• 底层主要是 SQLite + 可选 sqlite-vec 虚表。

  核心表是 memory_items：

  memory_items
  - id: 记忆 id，主键
  - memory_type: 记忆类型，比如 event / profile / preference / procedure
  - summary: 记忆摘要，也是关键词检索主要查的字段
  - content_hash: 摘要去重用的 hash
  - embedding: 向量 JSON 文本，作为 fallback 存储
  - reinforcement: 强化次数，命中排序/热度会用
  - emotional_weight: 情绪权重
  - extra_json: 扩展元数据，比如 scope_channel、scope_chat_id、trigger_tags、steps 等
  - source_ref: 来源引用，用来追溯原始消息或写入来源
  - happened_at: 事件发生时间
  - status: active / superseded 等状态
  - created_at / updated_at: 创建和更新时间

  还有几个辅助结构：

  ux_items_hash
  - unique(content_hash, memory_type)
  - 用来防重复写入

  consolidation_events
  - source_ref 主键
  - 记录某个来源是否已经 consolidation 过，避免重复处理

  memory_replacements
  - 记录 old_item -> new_item 的替换关系
  - 用于纠错、supersede、版本链追踪

  ix_items_status
  - status 索引
  - 因为检索通常只查 active 记忆

  向量检索如果 sqlite_vec 可用，会额外建：

  vec_items
  - sqlite-vec 虚表
  - embedding float[1024]

  这里有个关键点：

  > memory_items.embedding 保存原始 embedding JSON；vec_items 保存给 sqlite-vec KNN 用的 float blob，并通过 SQLite 的 rowid 和 memory_items.rowid 对齐。

  所以关键词检索查的是：

  memory_items.summary

  向量检索查的是：

  vec_items.embedding
  JOIN memory_items ON rowid

  一句话背诵版：

  > 底层是 SQLite。主表 memory_items 存记忆摘要、类型、embedding、来源、时间、状态和扩展元数据；关键词检索直接在 summary 上做 LIKE；向量检索优先用 sqlite-vec 的 vec_items 虚表做 KNN，再 join 回 memory_items 拿完整记忆。如果 sqlite-vec 不可用，就回退到扫描 memory_items.embedding 做 Python cosine。

# 关于querwrite

› 现在的问题改写querrewriteer是怎么做的？


• QueryRewriter 的做法是：用轻量 LLM 做语义改写，但用代码做超时、解析和失败兜底。

  它的入口是：

  QueryRewriter.decide(user_msg, recent_history)

  输出是一个 GateDecision：

  needs_episodic: 是否需要查历史事件/用户事实
  episodic_query: 改写后的历史记忆查询
  procedure_query: 改写后的偏好/流程规则查询
  latency_ms: 改写耗时

  核心流程：

  用户原始问题 + recent_history
    -> 并发跑两个 LLM 调用
        1. history gate / episodic query 改写
        2. procedure / preference query 改写
    -> 解析 XML 或纯文本
    -> 失败时 fail-open
    -> 返回 GateDecision

  第一路：history / episodic 改写

  它让 LLM 判断当前问题要不要查用户历史记忆。

  LLM 要输出 XML：

  <decision>RETRIEVE|NO_RETRIEVE</decision>
  <history_query>...</history_query>

  比如：

  用户：你还记得我用的是哪个 Fitbit 吗？

  会改写成：

  needs_episodic = true
  episodic_query = "用户使用的 Fitbit 设备型号"

  如果是：

  用户：你好

  会是：

  needs_episodic = false
  episodic_query = ""

  它还会用 recent_history 做指代消解，比如“那个项目”“它”“这东西”这种表述，会尽量改写成更具体的记忆查询。

  第二路：procedure / preference 改写

  这一路专门服务 procedure / preference 记忆。

  比如：

  用户：以后讲复杂问题先给我一个贯穿始终的例子

  它不一定需要查历史事件，所以：

  needs_episodic = false

  但会生成：

  procedure_query = "用户希望 agent 讲解复杂问题时先给贯穿始终的例子"

  再比如：

  用户：【视频标题-哔哩哔哩】 https://xxx

  会改写成：

  procedure_query = "用户发送哔哩哔哩视频链接时 agent 应如何处理"

  失败策略

  - 默认 timeout 800ms
  - 两路并发，互不阻塞
  所以它是 fail-open：

  > 宁愿用原始 query 查一下，也不要因为 query rewrite 失败导致完全不检索。

  一句话背诵版

  > QueryRewriter 是一个轻量 LLM 改写器。它把用户原话分成两类检索意图：一类是查历史事实的 episodic_query，一类是查偏好/流程规则的 procedure_query。它会结合 recent history 做指代消解，用 XML 判断是否需要检索历史；同时并发生成 procedure 风格查询。代码负责超时、解析和 fail-open，LLM 失败时回退到原始 query。当前代码里有这个模块和测试，但没有看到它默认接入主召回链路。

# 关于原始问题 改写与轻量假设

› 如果用户改写启用了，原始 query 进入召回；部分路径会额外生成 aux_queries 或轻量假设 query，用来增强向量召回这个还需要吗？


• 需要，但角色会变。

  如果 QueryRewriter 真正启用，链路不应该变成“只用改写后的 query”。更合理的是保留：

  原始 query
  + query rewrite 结果
  + 可选轻量假设 query / HyDE query

  原因是三者解决的问题不同：

  原始 query
    保留用户原话里的专有名词、版本号、工具名、拼写、原始表达。
    对关键词检索尤其重要。

  query rewrite
    把口语化、指代、省略的问题改成更接近 memory summary 的检索表达。
    比如“那个项目”改成“akashic-agent memory2 模块”。

  轻量假设 query / HyDE
    不是单纯改写问题，而是假设“如果记忆库里有这条记忆，它可能长什么样”。
    更偏向增强向量召回。

  所以启用后，我会设计成：

  用户问题
    -> QueryRewriter
        -> episodic_query / procedure_query
    -> 关键词 lane
        -> 优先用原始 query，必要时也可追加 rewrite query
    -> 向量 lane
        -> 原始 query + rewrite query + aux_queries / hypothesis
    -> RRF 融合

  为什么不能只用 rewrite query？

  因为 rewrite 可能丢信息。比如：

  用户：你还记得我之前说的 p6o34 那次 R3 稳定性结果吗？

  rewrite 可能改成：

  用户之前的记忆系统稳定性评估结果

  这更语义化，但可能丢掉关键字：

  p6o34
  R3

  这些对关键词检索非常重要。所以原始 query 仍要保留。
