# 写入治理离线计数评测

## 评测边界

本轮只评测 memory 写入阶段，不评测回答召回效果，也不接入真实 LLM。

- 测试集规模：`1200` 个写入候选。
- 难度拆分：`common = 600`，`hard = 600`。
- 类别拆分：6 类，每类 `200` 个候选。
- 子类型拆分：每类在 common/hard 下各 5 个子类型，每个子类型 20 个变体。
- 基线：原本写入方式，所有成功候选都视为写入，所以基线写入数是 `1200/1200`。
- 增强：叠加写入价值治理，`allow` 才写入，`reject` 和 `review` 都不直接写入。
- 离线保护：`offline_only = true`，`llm_calls_enabled = false`，`db_access_enabled = false`，`production_state_access_enabled = false`。
- 正式报告：
  - `my_md/memory_optimization/eval_reports/memory_write_governance_counts_eval.json`
  - `my_md/memory_optimization/eval_reports/memory_write_governance_counts_eval.md`

## 结论

写入治理的正向价值已经能被离线计数表体现：临时信息和助手推断污染都从原本 `200/200` 直接写入降到 `0/200`，污染候选总体控制率达到 `92.25%`。重复记忆也被控制了 `178/200`，说明当前重复风险规则对显式重复有效。

同时，这一轮也暴露了明显问题：有用候选保留率只有 `35.0%`，valuable preference 和 stable fact 都有 `130/200` 被拒绝或送复核。hard 子集里的有用候选直接写入为 `0/100`，说明当前写入评分更适合保守降噪，不适合作为最终自动写入策略。

冲突类也需要继续改进。期望冲突进入复核，但当前只有 `58/200` 进入复核，`102/200` 被直接拒绝，`40/200` 仍被直接写入。面试中应如实表达为：当前模块已经具备污染控制基础，但还需要增强冲突识别和复核分流，否则不能直接宣称写入治理已经达到线上可用。

## 后续计划

- 优先优化写入价值评分的有用候选保留能力，尤其是 hard preference 和 stable fact。
- 增强 conflict 检测，把“直接拒绝”和“直接写入”的冲突候选更多转入人工或策略复核。
- 在线测试必须等离线表稳定后再做；在线 evidence 应记录真实候选、真实决策、真实写入结果和后续召回有用率。
